Guidance for Claude Code (or any agent) working in this repository.

## What this is

`vendor-admins` is the **admin-only** business management panel for
TheAamGhar (Pakistani mango e-commerce). It is a real Next.js + TypeScript
app backed by a real Supabase project — **not** a demo, not mock data.

It is deliberately scoped to `/admin` routes only. The customer-facing
storefront is a separate concern (currently a static HTML/CSS/vanilla-JS
site at `E:\Claude\Theaamghar`, documented in its own CLAUDE.md and
`PRODUCTION_ROADMAP.md`) and may eventually be migrated to Next.js by a
different effort — this repo does not touch it.

There is also a `E:\Claude\admin-prototype\` folder from an earlier session:
a static, `localStorage`-only, fake-password mockup of an admin UI. It has
**no relationship** to this app beyond having inspired some early layout
ideas — it doesn't share auth, data, or schema. Don't port code from it
without re-checking it against the real schema/RLS model here.

## Auth architecture (layered, not one mechanism)

1. **`src/proxy.ts`** → `src/lib/supabase/proxy.ts` (`updateSession`):
   optimistic check only. Confirms *a* session exists via
   `supabase.auth.getClaims()` (never `getSession()`/`getUser()` in
   server-side code — Supabase's own docs warn `getSession()` isn't
   guaranteed to revalidate the token; `getClaims()` verifies the JWT
   signature every time). Redirects to `/login` if no session. Does **not**
   check `role` — that would mean a DB round trip on every request, which
   Next.js's own auth guide advises against for proxy-level checks.
2. **`src/lib/dal.ts`** (`getAdminUser`): the real authorization boundary.
   Confirms the session AND queries `profiles.role === 'admin'`, redirecting
   to `/login` otherwise. Called from `src/app/admin/layout.tsx`. Memoized
   per-request with React's `cache()`.
3. **Postgres RLS** (already in place from the storefront migrations, e.g.
   `admins update order status` / `admins manage products` policies using a
   `private.is_admin()` helper): the last line of defense if 1 or 2 are ever
   bypassed. Every new admin-writable table added here must get equivalent
   RLS policies (this is explicitly Phase 14 in the roadmap below, but new
   tables should get *basic* RLS immediately, not deferred).

There is **no separate admin password system** — auth is entirely Supabase
Auth (`profiles` has a comment to this effect from the original migration:
*"never store a separate admin password anywhere"*). The bootstrap admin
account is `admin@theaamghar.pk` (created directly via SQL insert into
`auth.users`/`auth.identities` since no MCP tool exists for creating
Supabase Auth users — see Gotchas below for the one bug hit doing this).

## Data conventions

- `orders.items` (jsonb array): `{ product_id, name, variety, qty, unit_price,
  box_size_kg?, product_type, variant_id, variant_source, variant_label,
  variant_attributes }`. Not DB-enforced (jsonb) — this exact shape is a
  documented contract the storefront checkout writes to. `box_size_kg` is
  present on every fruit line, old and new orders alike; non-fruit lines omit
  it and rely on `variant_label`/`variant_attributes` instead.
  `src/lib/order-item-label.ts`'s `getOrderItemLabel(item)` is the canonical
  reader — use it (e.g. in `OrderDetailClient.tsx`) instead of interpolating
  `box_size_kg` directly.
- `orders.delivery` (jsonb): `{ full_name, phone, address, city,
  postal_code, notes }`. Same caveat.
- **`products.product_type` (`'fruit' | 'clothing' | 'other'`) generalizes
  the catalog beyond mangoes** — added so the business can pivot categories
  from this admin panel without a rebuild. `fruit` is unchanged (still uses
  `product_box_sizes`, `origin`/`season`/`sweetness`/`fiber`/`weight_note`,
  `purchase_price_per_kg`); every other type uses **`product_variants`**
  (generic `attributes jsonb`, e.g. `{"size":"M","color":"Blue"}`, plus
  `selling_price`/`stock_qty`) as its variant table instead, `products.attributes
  jsonb` for type-specific product-level fields (e.g. clothing's
  fabric/fit/care_instructions/made_in), and `products.unit_cost` instead of
  `purchase_price_per_kg` for the profit calc. `src/lib/product-types.ts`
  drives both `ProductFormClient.tsx`'s conditional fields and the
  type-change guard in `products/actions.ts`'s `updateProduct()` (rejects
  changing `product_type` once a product has box sizes/variants or order
  history, via the `product_has_order_history` RPC). `product_box_sizes`
  itself is untouched by this.
- **Inventory (`src/lib/queries/inventory.ts`) merges both variant tables**
  into one `InventoryUnit` shape (`{id, source, product_id, product_name,
  label, stock_qty, low_stock_threshold, active, state}`) so clothing stock
  surfaces in `InventoryClient.tsx` alongside fruit box sizes without two
  separate UIs; `adjustStock`/`updateThreshold` in `inventory/actions.ts`
  branch on `source` to target the right table.
- **`order_item_stock_warnings` is where the stock/profit triggers
  (`adjust_stock_for_order_items`, `calculate_order_profit`) log instead of
  silently no-op-ing**: an order line that can't be resolved to a real
  `product_box_sizes`/`product_variants` row now lands here (admin-readable,
  no anon/authenticated write access) rather than silently skipping the
  stock adjustment or costing the line at 0. If stock/profit numbers ever
  look wrong, check this table first.
- `orders.status`: `pending | confirmed | packed | shipped | delivered |
  cancelled | refunded` (migrated from the storefront's original narrower
  set in `extend_orders_for_admin_dashboard`).
- `orders.profit` / `orders.cost_snapshot`: populated by the Phase 2 cost
  engine at order-creation time — a **snapshot**, not a live recomputation,
  so historical reports stay accurate even after product costs change later.
- Currency formatting: `formatPKR()` in `src/lib/format.ts` — mirrors the
  storefront's `formatPKR` in `js/products.js` (`'Rs ' + toLocaleString('en-PK')`)
  so the two apps never drift.
- Dashboard stats/charts (`src/lib/queries/dashboard.ts`) are computed by
  fetching up to 365 days of orders and aggregating in JS, not bespoke SQL
  (`jsonb_array_elements`, `date_trunc`, etc.). Deliberate choice for
  correctness/simplicity at this order volume — revisit only if Phase 15
  (performance) finds it's actually a bottleneck.

## Local dev gotchas already solved here

- **Node.js was not installed on this machine** at project start — it was
  installed via `winget install -e --id OpenJS.NodeJS.LTS`. The harness's
  own shell tools (Bash/PowerShell) don't pick up a `SetEnvironmentVariable`
  PATH change made mid-session (new processes spawned by the harness's
  parent don't re-read the registry), so every Bash call that needs
  `node`/`npm` must prefix: `export PATH="/c/Program Files/nodejs:$PATH"`.
- **`.claude/launch.json`**'s `vendor-admins` entry can't just run `npm`
  directly for the same PATH reason — it points at `vendor-admins\dev.bat`,
  a tiny wrapper that sets PATH then runs `npm run dev`. Don't "simplify"
  this back to a bare npm command; it'll silently fail to find `node`.
- **GoTrue (Supabase Auth) 500 on sign-in after seeding a user via raw SQL**:
  if you ever need to create another Auth user directly via SQL (there's no
  MCP tool for it), `auth.users.email_change` and `email_change_token_new`
  **must be `''`, not `NULL`**, even though the column is nullable — GoTrue's
  Go SQL scanner errors on NULL there (`converting NULL to string is
  unsupported`). This cost real debugging time; don't reintroduce it.

## The 17-phase build

This admin panel is being built in the 17 phases the client specified
(business dashboard → profit calculator → seasonal pricing → shipping →
inventory → products → orders → customers → coupons → analytics → settings
→ reports → notifications → security → performance → UI/UX polish → final
QA). Track progress with the session's TaskList (17 tasks, one per phase)
rather than re-deriving status from scratch each session — check that first.

**All 17 phases are complete.** schema/dashboard, profit calculator, varieties &
seasons, shipping zones, inventory (stock states + audit log + auto
decrement/restock triggers), full product CRUD (multi-image upload to the
`product-images` bucket, box sizes), order management (status pipeline,
tracking, bulk actions), customers, coupons, analytics (custom date range +
period-over-period comparison), settings, reports (CSV/Excel/PDF via
`exceljs`/`pdfkit`), notifications (Realtime `admin_notifications` feed + DB
triggers for new orders/cancellations/low-stock), a security hardening pass,
a performance pass (pagination + indexing + RLS policy consolidation), a
UI/UX polish pass (theme toggle, loading skeletons, responsive audit), and
final QA (lint/build both fully clean, every route smoke-tested with zero
console errors, DB confirmed free of leftover test data).

**Important honesty note for whoever continues this**: every dashboard
number will legitimately read zero/empty until the real customer storefront
starts writing real orders into this schema — that's correct behavior per
"no mock data," not a bug. Don't be tempted to seed fake orders to make the
dashboard "look alive."

**Verification pattern used throughout**: every phase was checked by
inserting a real temporary row via `execute_sql`, exercising the UI/action in
the browser, confirming the DB write with another `execute_sql` query, then
cleaning up. When a test order needs removing, always flip its `status` to
`cancelled` first (via SQL or the UI) and only delete afterward — deleting an
`orders` row directly skips the `orders_restock_after_cancel_refund` trigger
and leaves `product_box_sizes.stock_qty` permanently off by the order's qty.
This was gotten wrong twice during Phases 7/8/10 and had to be corrected with
manual `manual_adjustment` audit-log entries — don't repeat it.

## Phase 14 security hardening — findings and fixes

- **`profiles` had no admin-UPDATE RLS policy** — only `auth.uid() = id`
  (self-update). The Phase 8 "edit customer profile" admin action silently
  updated 0 rows (Supabase returns no error on an RLS-filtered 0-row update).
  Fixed by adding an `admins update any profile` policy using
  `private.is_admin()`. If a future admin-facing update on any table seems to
  silently no-op, suspect a missing admin RLS policy first — the update
  call itself won't error.
- **Six `SECURITY DEFINER` trigger/helper functions were callable directly by
  anon/authenticated via PostgREST's auto-generated `/rest/v1/rpc/*`**:
  `adjust_stock_for_order_items`, `handle_order_insert_stock`,
  `handle_order_status_restock`, `notify_new_order`,
  `notify_order_status_change`, `notify_stock_threshold`. The first one is
  especially dangerous since it takes plain arguments (not `NEW`/`OLD`) —
  anyone could have called it directly to manipulate any product's stock.
  Fixed via `revoke execute ... from public` (not just `from anon,
  authenticated` — Postgres grants EXECUTE to the `PUBLIC` pseudo-role by
  default on function creation, and revoking from specific roles alone does
  **not** remove privilege inherited through `PUBLIC`; verify with
  `has_function_privilege('anon', oid, 'EXECUTE')`, not just by re-running
  `get_advisors` immediately — its lint cache can lag behind a just-applied
  migration). Confirmed the actual order-insert/cancel and stock triggers
  still fire correctly after the revoke (trigger execution doesn't depend on
  the invoking role's EXECUTE grant on the trigger function).
- **`auth_leaked_password_protection` advisory (HaveIBeenPwned check) is
  disabled** — this is a Supabase Auth service setting with no SQL/migration
  or MCP tool to toggle it from here. Needs to be enabled manually via the
  Supabase Dashboard → Authentication → Policies (or the equivalent Auth
  settings page) by someone with dashboard access.
- Every other table added in Phases 2–13 (`product_box_sizes`,
  `business_settings`, `shipping_zones`, `inventory_audit_log`, `coupons`,
  `admin_notifications`) was audited and has RLS enabled with policies
  matching intent (admin-only CRUD via `private.is_admin()`, plus narrow
  public SELECT only where the storefront will eventually need it —
  `shipping_zones` default rates and published `products`/`product_box_sizes`
  rows). `coupons` and `admin_notifications` are deliberately admin-only with
  **no** public SELECT — see the code comment on the `coupons` migration for
  why (codes shouldn't be enumerable; validate them through a future
  security-definer RPC instead of direct table access).
- Every Server Action across every phase re-calls `getAdminUser()` as its
  first line (verified via `grep -c` — one call per exported action, matching
  the count of exported functions in each `actions.ts`, the one exception
  being `signOut()` which correctly needs no admin check). The three
  `/api/admin/reports/*` route handlers do the same.
- **Update (post-Phase-14):** a service-role key now exists — `SUPABASE_SERVICE_ROLE_KEY`
  in `.env.local`, used by `src/lib/supabase/admin.ts`'s `createAdminClient()`
  for the customer email-change feature (`auth.admin.updateUserById`, which
  needs to bypass RLS and call the Auth Admin API). It's implemented
  correctly: `server-only` import guard, no `NEXT_PUBLIC_` prefix, `.env*`
  gitignored, only ever called from Server Actions after `getAdminUser()`.
  Keep it that way — never move this key to a client-accessible variable or
  call `createAdminClient()` before the admin check.
- A follow-up security pass (post-Phase-14) added `admin_audit_log`
  (`src/lib/audit-log.ts`'s `logAdminAction()`, called from the orders/
  customers/coupons/products Server Actions after each write) and DB-side
  login rate-limiting (`check_and_record_login_attempt`/`reset_login_attempts`
  RPCs, backing table `private.login_attempts` — RLS-locked with zero
  policies so it's only reachable through those two `SECURITY DEFINER`
  functions, called from `src/app/login/actions.ts`). The audit trail is
  viewable in-panel at `/admin/audit-log` (`src/app/admin/audit-log/`, nav
  under Settings; paginated + entity/action filters via
  `src/lib/queries/audit-log.ts`) so it's not SQL-only. Also added baseline
  security headers (CSP, X-Frame-Options, HSTS, etc.) in `next.config.ts`.
  **Update (post-Phase-14, round 2):** TOTP MFA is implemented end-to-end —
  `src/app/admin/settings/mfa-actions.ts` + `MfaClient.tsx` (enroll/verify/
  unenroll, Settings → Two-Factor Authentication) and `src/app/login/mfa/`
  (the aal1→aal2 challenge step after password sign-in). `src/lib/dal.ts`'s
  `getAdminUser()` enforces aal2 for any account with a verified factor, not
  just the login action, so an already-open aal1 session can't bypass it.
  Off by default (no factor enrolled on the real account yet) — enroll it
  yourself in Settings once you have an authenticator app ready. Also added
  IP allowlisting (`src/lib/ip-allowlist.ts`, checked in
  `src/lib/supabase/proxy.ts` before any Supabase call): a no-op unless the
  `ADMIN_IP_ALLOWLIST` env var is set (comma-separated exact IPs and/or
  IPv4 CIDR ranges), deliberately an env var rather than a DB setting so it
  can't be loosened from inside a compromised admin session.

  Three settings remain dashboard-only — no SQL/migration/MCP path exists:
  - **Leaked-password protection** (HaveIBeenPwned check on sign-up/
    password-change): Supabase Dashboard → project → Authentication →
    Policies (or Auth → Settings) → enable "Leaked password protection".
  - **Point-in-Time Recovery**: Supabase Dashboard → project → Database →
    Backups → enable PITR (paid add-on beyond the free tier).
  - **Vercel preview-deployment protection**: Vercel Dashboard →
    `vendor-admins` project → Settings → Deployment Protection → enable
    protection for Preview deployments.

## Phase 15 performance pass — findings and fixes

- **Orders list is paginated** (`getOrdersList(statusFilter, page)` in
  `src/lib/queries/orders.ts`, `ORDERS_PAGE_SIZE = 25`) using Supabase's
  `.range()` + `{ count: 'exact' }` — the only table in this app expected to
  grow unbounded over time. Every other list (products, customers, coupons,
  inventory) stays a full fetch since catalog/customer/coupon counts for a
  single-vendor business remain small; revisit only if that stops being true.
- **`orders.created_at` had no index at all** despite being the most-queried
  column in the app (dashboard, analytics date range, orders list sort,
  customer order history) — added. Also added `orders.status` (used by the
  orders list filter) and the missing FK-covering index on
  `inventory_audit_log.order_id`.
- **Consolidated two RLS performance warnings** (`get_advisors(type:
  'performance')` flags `multiple_permissive_policies` when a table has more
  than one permissive policy for the same role+action, since Postgres
  evaluates all of them per query): `profiles` had separate self-update and
  admin-update-any UPDATE policies, merged into one `using (auth.uid() = id
  or private.is_admin())`; `shipping_zones` had a `FOR ALL` admin policy
  overlapping a public-read SELECT policy, split into per-command
  INSERT/UPDATE/DELETE admin policies plus one merged SELECT policy
  (`active = true or private.is_admin()`). Both re-verified end-to-end
  through the actual UI after the change, not just by re-running the
  advisor.
- Remaining advisor output is informational-only (`unused_index` on indexes
  that are simply new / this app has near-zero real traffic yet) — not
  something to "fix" by removing them.

## Phase 16 UI/UX polish — what was added

- **Manual light/dark theme toggle** (`src/components/admin/ThemeToggle.tsx`,
  cycles system → light → dark, persisted to `localStorage` under
  `theaamghar_admin_theme`) in the Topbar, plus a pre-paint inline script in
  `src/app/layout.tsx` (`THEME_INIT_SCRIPT`) that applies the saved
  preference to `<html data-theme>` before first render, mirroring the
  storefront's flash-prevention convention. **This requires
  `suppressHydrationWarning` on the `<html>` tag** — without it, React logs a
  hydration-mismatch error every load because the script intentionally sets
  an attribute the server-rendered HTML doesn't have. This was a real bug
  caught during this pass (verified via a fresh browser tab, since an
  already-open tab keeps stale console history from before the fix — don't
  trust `read_console_messages` on a tab that's been open across a code
  change; open a new tab to get a clean read).
- **`loading.tsx` skeletons** (`src/components/admin/Skeleton.tsx` +
  per-route files) for the data-heaviest pages: dashboard, orders, products,
  customers, analytics, inventory. Other pages (varieties, shipping,
  coupons, settings, profit calculator, reports) fetch small/bounded data
  and were left without one deliberately — not an oversight.
- **Responsive audit**: verified at 375px width (mobile) that the sidebar
  sits off-canvas by default (`left: -256px`) with the hamburger toggle
  visible, and that wide tables scroll within their own `.overflow-x-auto`
  wrapper rather than blowing out page width — checked via computed
  `getBoundingClientRect()`/`scrollWidth` since this environment can't take
  real screenshots.
- Empty states were already consistent from earlier phases (`EmptyState`
  component on every dashboard/analytics chart, honest "no X yet" copy on
  every list page) — audited, no gaps found.

## Phase 17 final QA — what was checked

- **`npm run lint` is fully clean** (0 errors, 0 warnings) — it was not
  before this pass. `eslint-config-next`'s `react-hooks` plugin (the
  React Compiler rule set) flagged ~10 `react-hooks/set-state-in-effect`
  errors: the "toast + reset form fields" pattern used after every
  `useActionState` submission across this app (coupons, inventory, orders
  bulk-update, shipping, profit calculator, theme toggle) triggers it,
  because the rule generally wants side effects to avoid `setState` inside
  `useEffect`. Each one was individually judged, not blanket-suppressed:
  they're all legitimate exceptions (no callback exists on `useActionState`
  results other than watching them via effect; localStorage isn't readable
  during SSR so it can't be a lazy `useState` initializer without causing a
  *different* hydration-mismatch bug) and got a scoped
  `eslint-disable-next-line react-hooks/set-state-in-effect` with a comment
  explaining why. Also fixed for real (not disabled): a `Date.now()` call
  directly in a component body (`react-hooks/purity` — moved into a
  `useState(() => Date.now())` lazy initializer so it only runs once at
  mount), two unescaped `'` characters in JSX text (`react/no-unescaped-entities`),
  and two unused-variable warnings from destructure-and-omit patterns
  (replaced with explicit object construction).
- **`npm run build` passes clean** — final run, no type errors.
- **Every admin route was smoke-tested** in a fresh browser tab (dashboard,
  products, products/new, orders, customers, varieties, inventory,
  profit-calculator, shipping, coupons, analytics, reports, settings) with
  zero console errors. Confirmed `/login` correctly redirects an
  authenticated session back to `/admin` (proxy auth guard still works).
- **Database confirmed clean of test data**: 0 rows in `orders`,
  `admin_notifications`, `coupons`, and non-admin `profiles`; the real
  6-product catalog and its legitimately-restocked inventory (80 total units
  across Sindhri's 3kg/5kg box sizes — genuine data from earlier phases'
  manual-adjustment testing, not leftover pollution) are intact.
- Final `get_advisors(type: 'security')` run: only the one known
  dashboard-only item remains (`auth_leaked_password_protection` — see
  Phase 14 notes above for why it can't be fixed from here).
